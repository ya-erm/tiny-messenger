# Независимый прототип Яндекс Облака

Cloud Functions (Node.js 22, 256 МиБ) → YDB Serverless, вход через API Gateway.
VPS не участвует ни в авторизации, ни в чтении, ни в записи облачного контура.
Ключ управления остаётся на VPS; функция использует собственный сервисный аккаунт.

Поддерживаются вход с существующим токеном, контакты/поиск, личные и групповые
сообщения, правки, реакции, удаления, цитаты, опросы, файлы и подтверждения
прочтения. Общие protocol/reducer и правила слияния строк генерируются из VPS.
Пользователи, смена токена, профили и контакты обновляются из VPS в облако;
изменять их пока можно только через VPS API. Регистрация остаётся на VPS.

Начиная с 0.11.0 данные сообщений, группы, участники, метаданные файлов и опросы
реплицируются в обе стороны. Бинарные файлы используют общее приватное S3-хранилище;
каждый контур сам проверяет доступ и подписывает URL, без обращения к VPS API.
Это резервирование API и данных в SQLite/YDB, но не независимая копия S3-файлов.

Клиент объединяет локальную историю выбранных каналов в IndexedDB. Устойчивая
клиентская очередь пока покрывает обычный личный текст; файл/группа/опрос не имеют
такой же фоновой офлайн-очереди. Повтор отправки в текущей сессии сохраняет ID.
Звонки и существующие push-уведомления остаются на VPS. Облачные сообщения
приходят при открытом приложении через опрос изменений раз в 5 с.
Статика пока раздаётся с VPS, перенос и зеркала — следующий этап.

## Адреса

| Канал | API |
| --- | --- |
| По умолчанию | `https://api.tm.ya-erm.ru` |
| Канал 1 (VPS) | `https://ch-1.api.tm.ya-erm.ru` |
| Канал 2 (Яндекс Облако) | `https://ch-2.api.tm.ya-erm.ru` |

Фактический TTL записей на NS REG.RU — 3600 с; переключение основного CNAME
может быть видно клиентам с задержкой до часа. Общая SOA зоны не менялась,
поскольку её используют и другие проекты.

Основной DNS CNAME сейчас указывает на фиксированный VPS-канал. Для переключения
основного меняется только его CNAME. Выбор в настройках браузера сохраняется;
автоматического переключения между контурами пока нет.

## Развёртывание

Приватные настройки и ключи — `.secrets/yandex-cloud/` (каталог 0700, файлы 0600).
`service-account.json` — авторизованный JSON-ключ; `target.json` содержит `folderId`,
`folderName`; `deployment.json` хранит ID уже созданных ресурсов и endpoint YDB.
Никакие файлы этой папки не попадают в Git, Docker build context или ZIP функции.

1. `node scripts/yandex-provision.mjs` — создать/найти сервисный аккаунт и YDB.
2. Установить зависимости отдельного `cloud/yandex/package-lock.json` через `npm ci`
   в Node.js 22; на общем сервере ограничивать CPU/память контейнера.
3. `node scripts/build-cloud-prototype.mjs` — сгенерировать общий протокол.
   Использует TypeScript из установленного релиза (`deploy/release.env`).
4. `node --test cloud/yandex/tests/service.test.mjs` — проверить контракт.
5. `python3 scripts/package-cloud-prototype.py` — собрать ZIP по белому списку.
6. `node scripts/deploy-cloud-prototype.mjs` — опубликовать новую версию функции,
   создать/найти шлюз. Каждое выполнение действительно публикует новую версию.
7. Начальный экспорт `scripts/export-cloud-bootstrap.py`, затем импорт
   `node scripts/seed-cloud-prototype.mjs`. Экспорт приватный; импорт сохраняет
   уже существующие записи. Это начальная загрузка, не средство синхронизации.

TLS: сертификат Certificate Manager содержит основной и облачный API-домены.
DNS CNAME `_acme-challenge` нужно сохранить для автоматического продления.
Привязка доменов к шлюзу требует выпуска сертификата и свободной квоты
`serverless.apiGatewaysDomains.count`. На момент настройки запрос отклонён с 429,
а Quota Manager не поддерживает эту квоту (запрос изменения — 403).
Нужно увеличить квоту «Количество доменов в одном облаке» минимум на 2.
До этого явно выбранный Яндекс-канал при сетевой ошибке своего поддомена обращается
к служебному HTTPS-адресу того же шлюза (не к другой инсталляции). На 5 минут
запоминает успешный запасной адрес, затем снова пробует собственный домен.
Основной и VPS-каналы автоматически в другой контур не переключаются.

## Ограничения и следующий этап

YDB: 0 выделенных RU/s, ограничение 100 RU/s, хранилище 1 ГиБ, защита от удаления.
Функция: 0 подготовленных экземпляров, 1 запрос на экземпляр,
максимум 1 экземпляр на зону, таймаут 15 с. Это ограничивает нагрузку,
но не задаёт жёсткий лимит расходов за месяц. Логи WARN, без текстов/токенов.

Прототип хранит операции одного сообщения в одной JSON-записи (до 1 МиБ).
Снимок содержит последние 100 записей; удалённые записи занимают место в этом
окне. Глобальный счётчик последовательности подходит небольшой нагрузке.
Для роста нужны раздельные записи операций, курсоры/индексы по чатам,
компактация и сборка журнала. Локальный журнал клиента пока не очищается.

Следующие этапы — полная пагинация истории, ограничение сроков хранения,
компактация журналов и независимые копии бинарных файлов. Журналы пока сохраняются
целиком. Начальный перенос использует оригинальный снимок от первого запуска
облака; заменять его свежим экспортом нельзя.

## Репликация v1

VPS вызывает `POST /api/internal/replication/exchange` облачного шлюза. Отдельный
случайный ключ проверяется до подключения к YDB; обычный токен пользователя
не даёт доступа к импорту или экспорту. В пакетах явно проверяются версия,
идентификаторы источника/получателя, порядок курсоров и ограничения размера.
Ключ передаётся только по HTTPS, не попадает в браузер, Git, ZIP или логи.
Ключ управления Яндекс Облаком функции не передаётся.

- Пакет — до пяти операций и пяти изменившихся записей справочника, запрос до
  512 КиБ. Справочник включает пользователей, контактные списки и известные ID
  прочтённых/доставленных сообщений. Неизменившиеся данные повторно не передаются.
- На VPS локальный журнал проверяется раз в две секунды. При исправной шине
  операции отправляются через неё, контрольный HTTP-обмен — раз в 30 минут.
  Справочник и личные подтверждения прочтения по-прежнему передаются через HTTP
  сразу после изменения. Без шины: 60 секунд в простое, пять секунд в течение
  двух минут после активности. Догоняющий обмен — пакетами раз в две секунды.
- При ошибке — экспоненциальная пауза от пяти секунд до пяти минут, в том числе
  при оставшихся исходящих операциях. При недоступном VPS облако продолжает
  обслуживать пользователей самостоятельно; изменения накапливаются в YDB.
- Курсор облака и подтверждение исходящего журнала сохраняются в SQLite вместе
  с импортированными изменениями. Потерянный ответ и частично принятый пакет
  безопасно повторяются по operationId. Импорт в облако не порождает новый
  исходящий журнал; обратное эхо VPS подавляется облачной дедупликацией.
- В облаке используется отдельная служебная лента в существующей tm_feed;
  быстрая шина использует отдельные приватные очереди YMQ. Пустой HTTP-обмен
  выполняет только чтение. Работают прежние
  ограничения: 0 подготовленных функций, 256 МиБ, 0 выделенных RU/s.
- Прочтения объединяются по ID, без переноса облачного watermark на VPS:
  позднее сообщение само по себе не становится прочитанным. На самом VPS
  прежние локальные API всё ещё используют временные watermarks.
- Удаление имеет приоритет над поздней правкой. Исходные операции, в том числе
  текст удалённого сообщения, пока остаются в закрытых журналах обеих баз:
  физическое стирание/компактация — отдельный этап.
  Начальный снимок передаёт явные ID удалений, чтобы старый кэш другого канала
  не восстанавливал удалённые сообщения после переключения. Это не защищённый от удаления
  резерв: логическое удаление распространяется на обе инсталляции.

Первое включение:

1. Создать приватный `.secrets/yandex-cloud/replication.json`: `url` облачного
   служебного входа, случайный `secret` (не менее 32 байт/символов),
   `installationId: "vps-1"`, `peerId: "yandex-1"`,
   `bootstrapFile: "/app/data/replication-bootstrap.json"`.
2. Скопировать конфигурацию в `data/replication.json`, а **оригинальный** снимок
   начальной загрузки — в `data/replication-bootstrap.json`. Владелец uid 1001,
   режим 0600. Не заменять исходный снимок новым экспортом: из него вычисляются
   те же детерминированные ID старых операций, что при загрузке облака.
3. Проверить историю на копии базы: `scripts/replication-history-dryrun.mts`.
   Перед первым обменом VPS атомарно включает старый личный текст в журнал и
   добавляет изменения/удаления, сделанные после начальной загрузки.
4. Собрать/опубликовать облачную функцию; deploy-скрипт добавляет отдельный ключ
   из приватной конфигурации. Затем `node scripts/backfill-cloud-replication.mjs`:
   один раз включить существующие облачные операции и прочтения в служебную ленту.
   Скрипт повторяемый; предел — 10 000 записей, далее нужна пагинация.
5. Установить новый VPS-релиз с миграцией и добавить в `.env`
   `TM_REPLICATION_CONFIG=/app/data/replication.json`. Пересоздать только Messenger.
   `python3 scripts/replication-status.py` показывает успех/ошибку и очередь,
   не раскрывая содержимое сообщений или секреты.

Отключение фонового обмена: убрать `TM_REPLICATION_CONFIG` из `.env` и пересоздать
только Messenger. Оба контура сохраняют данные и продолжают работать отдельно.
Не удалять курсоры/журналы для «исправления»: после восстановления старой копии
базы нужно отдельно согласовать положение курсоров и повторить безопасный импорт.
Курсор, опережающий облачный журнал, отклоняется, а не сбрасывается автоматически.

Фон без активности: `30 × 24 × 60 = 43 200` запросов в месяц, независимо от числа
пользователей. Если постоянно держится активный режим: до 518 400 пустых опросов
в месяц; передача очереди добавляет запросы. Это **добавка** к клиентскому трафику.
По тарифам ниже 43 200 вызовов сами по себе входят в бесплатные пакеты запросов,
но бесплатный объём общий для платёжного аккаунта; выполнение функций и RU
тоже должны укладываться в свои пакеты. Гарантии нулевого счёта нет.

## Оценка расходов (тарифы проверены 19 ноября 2026)

За месяц при 256 МиБ и суммарном округлённом времени выполнения `S` секунд:

- Functions: `18,97 × max(0, N−1 000 000)/1 000 000 + 6,48 × max(0, 0,25×S/3600−10)` ₽.
  Время округляется вверх по 100 мс **для каждого** вызова.
  [Тариф Functions](https://yandex.cloud/ru/docs/functions/pricing).
- Gateway: `142,30 × max(0, G−100 000)/1 000 000` ₽.
  `G` включает запросы preflight OPTIONS, не только полезные запросы.
  [Тариф API Gateway](https://yandex.cloud/ru/docs/api-gateway/pricing).
- YDB: `24,64 × max(0, RU−1 000 000)/1 000 000` ₽ по on-demand;
  1 ГиБ хранения входит в free tier, выделенная пропускная способность выключена.
  [Тариф YDB](https://yandex.cloud/ru/docs/ydb/pricing/serverless),
  [бесплатный объём](https://yandex.cloud/ru/all-offers).

Бесплатные пакеты могут расходоваться другими ресурсами того же платёжного аккаунта.
Ключевой расход — периодический опрос при открытом окне, даже если сообщений нет.
При 5 с между опросами: `число пользователей × часов в день × 720 × 30` запросов
за 30 дней. Закрытая/невидимая вкладка перестаёт опрашивать API; голос — отдельный VPS.

Расчёт ниже **иллюстративный**, не замер биллинга. Предположения: по 1 часу в день
на пользователя, среднее оплачиваемое время 300 мс, 5 RU на запрос, пустой free tier,
хранилище до 1 ГиБ. Не включает сообщения, первоначальные снимки, OPTIONS,
дополнительные устройства/вкладки, логи и исходящий трафик сверх бесплатного объёма.

| Пользователей | Опросов за месяц | Gateway | Functions | YDB | Всего |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 5 | 108 000 | 1,14 ₽ | 0 ₽ | 0 ₽ | ≈1 ₽ |
| 26 | 561 600 | 65,69 ₽ | 11,02 ₽ | 44,55 ₽ | ≈121 ₽ |

Фактические RU зависят от CPU, количества и размера прочитанных/записанных строк,
а не равны числу HTTP-запросов. Изменение сообщения дороже пустого опроса:
журнал, состояние, две проекции и две записи ленты пишутся в одной транзакции.
[Как считаются RU](https://yandex.cloud/ru/docs/ydb/pricing/ru-yql).
До полного перевода стоит измерить реальный день использования через биллинг и
снизить частоту опроса без активного диалога. Резерв, которым пользуются изредка,
при небольшой нагрузке может целиком уложиться в бесплатные пакеты.


## Расширенная репликация и шина (0.11.0)

`ReplicaChange` — транзакционный исходящий журнал SQLite: триггеры записывают
изменения 12 таблиц. `ReplicaRow` хранит данные и версии каждого поля, включая
удаления. Импорт подавляет триггеры, поэтому не порождает бесконечное эхо.
В YDB используются такие же состояния и общая функция слияния из `rows.ts`.
Версия сравнивается по UTC-времени, источнику, локальной последовательности и ID.
Правки разных полей объединяются; удаление сообщения/группы побеждает правки.
Членство и реакции допускают повторное добавление более новой операцией.
Ответ на опрос выбирается по самому раннему времени ответа, затем по версии;
курсоры прочтения объединяются по максимуму. Вложения сохраняют связь с сообщением,
даже если из другого контура позднее пришла устаревшая отметка очистки.

Конверт шины `version/from/to/id/at/kind/events` не зависит от YMQ. Он содержит
сами операции (до пяти), а не только сигнал для дополнительного HTTP-запроса.
Адаптер предоставляет `publish`, `receive`, `acknowledge`; операции применяются
общим обработчиком с HTTP-репликацией. MQTT сможет использовать тот же конверт,
но потребует отдельного адаптера и отдельной подписки для каждой инсталляции.
Общая конкурирующая подписка, распределяющая события между серверами, не подходит.
Сейчас настроены два контура; добавление третьего также требует настройки начального
переноса и резервного обмена для новых пар источников.

У каждого получателя своя очередь. VPS слушает исходящим HTTPS long polling
с ожиданием до 20 секунд: при поступлении сообщения ответ возвращается сразу.
Облако получает события триггером функции, без постоянно работающей функции.
Подтверждение очереди происходит после сохранения. При потере ответа событие
повторится; ID и версии обеспечивают идемпотентность. Журнал и HTTP-курсоры
независимы от подтверждения шины и позволяют восстановиться после потери очереди.
Один запрос шины может содержать несколько мутаций.

Раз в минуту VPS отправляет ping, облако отвечает pong и повторяет неотправленную
часть своего журнала. Отсутствие подтверждения 125 секунд или ошибка транспорта
отключают режим редкого HTTP-обмена. Затем действует минутный резервный опрос
(после активности чаще); обнаружение отказа и сам опрос добавляют задержку.
Это не обещание доставки за минуту при любом отказе. При недоступном облаке
повторы HTTP имеют экспоненциальную паузу до пяти минут.

Доступ к очередям закрыт IAM, в runtime передаётся отдельный статический ключ
с правами чтения/записи очередей, а не ключ управления облаком. Передача по HTTPS;
дополнительного прикладного шифрования содержимого нет. Тексты не пишутся в логи.
`bus.json`, runtime-конфигурация и резервные копии конфигурации остаются приватными.

Включение:

1. `node scripts/provision-replication-bus.mjs` создаёт/находит очереди и выделенный
   сервисный аккаунт; сохраняет параметры только в `.secrets/yandex-cloud/bus.json`.
2. Перед первым включением сохранить в `bus.json.bootstrapCursor` подтверждённый
   облачный курсор текущей реплики: старые события уже доставлены через HTTP.
3. Сначала опубликовать совместимую функцию: сборка общего протокола, упаковка
   и `deploy-cloud-prototype.mjs`. S3-настройки берутся из разрешённых полей `.env`.
4. В приватный `data/replication.json` добавить `bus`: `enabled`, `provider: "ymq"`,
   `endpoint`, `region`, `credentials`, `inbox` (своя очередь),
   `targets: [{installationId, address}]`. Сохранить старую конфигурацию для отката.
5. Установить проверенный релиз VPS с совместимой миграцией. Затем
   `node scripts/provision-replication-bus.mjs --trigger` включает облачного получателя.
6. Проверить двустороннюю доставку на синтетических аккаунтах и контрольные курсоры.
   Для отключения вернуть конфигурацию без `bus` и перезапустить только Messenger;
   HTTP-репликация продолжит работать. Старый релиз без поддержки строк не должен
   использоваться для длительного отката после появления новых групповых операций.

Проверки: `scripts/test-rich-replication.mjs`, `scripts/test-bus-replication.mjs`,
`cloud/yandex/tests/row-conflicts.test.mjs`, `cloud/yandex/tests/bus.test.mjs`,
`scripts/replication-bus/transport.test.mjs`. Они проверяют обе стороны, потерю
подтверждения, повтор, отсутствие эха, отказ шины, права групп и доступ к файлам.
`scripts/extended-replication-dryrun.mts` запускается только на копии SQLite и
проверяет неизменность всех пользовательских таблиц при первом включении журнала.

YMQ Standard: первые 100 тыс. операций в месяц бесплатны, затем 57,82 ₽ за миллион
([тариф](https://docs.yandex.cloud/ru/message-queue/pricing)). Чтение/удаление
триггером Functions не тарифицируется в YMQ. Простой VPS long polling даёт около
129 600 запросов за 30 дней; с минутными ping/pong суммарно ориентировочно
300 тыс. операций, то есть около 12 ₽/месяц за очередь после бесплатного пакета.
Это оценка для двух контуров, без пользовательского трафика. Heartbeat также даёт
43 200 вызовов функции и чтения YDB; общие бесплатные пакеты могут их покрыть,
но стоимость зависит от фактического времени функции, RU и других ресурсов аккаунта.
