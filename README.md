# Tiny Messenger

Небольшой личный мессенджер для веба и устройства с экраном 0.96″ 80×160 px и тремя кнопками. Пользователю не нужна регистрация: сервер выдаёт UUID и секретный токен, который одновременно служит паролем и API-ключом.

## Что уже работает

- создание профиля и восстановление на другом браузере по токену;
- смена короткого имени и ротация токена;
- единый поиск контактов по имени, нику или UUID с актуальными данными профиля;
- обычные сообщения и вопросы с ответами `left` / `right`;
- статусы `sent` → `delivered` → `read` → `answered`;
- входящие и ответы из веб-интерфейса;
- установка как PWA и Web Push-уведомления о сообщениях и ответах;
- голосовые WebRTC-комнаты 1:1 с повторным входом, reconnect и выбором аудиоустройств;
- presence контактов: «В сети» и сохранённое время последнего подключения;
- REST polling для ESP и веба, а также WebSocket device adapter на общем HTTP-сервере;
- атомарное JSON-хранилище, общий minute-window rate limit и отдельная защита от слишком быстрой отправки сообщений;
- Docker-сборка с единым Next.js custom server для VPS.

Текущие серверные defaults:

| Поле | Максимум |
| --- | ---: |
| Имя на устройстве | 14 символов |
| Сообщение | 96 символов |
| Подпись каждой из двух кнопок | 5 символов |

Они возвращаются через `GET /api/config` и могут измениться, в том числе стать пользовательскими настройками. Клиентам не следует считать эти числа неизменной частью протокола. Сервер считает Unicode code points, а не байты UTF-8; прошивке всё равно нужно учитывать реальную ширину глифов, перенос и возможную прокрутку.

## Локальный запуск

Нужны Node.js 20.9+ и pnpm 9.15.

```bash
pnpm install
pnpm dev
```

Откройте `http://localhost:3000`. Рабочие данные появятся в `data/store.json` и не попадут в git.

Проверки:

```bash
pnpm typecheck
pnpm build
```

Smoke-тест ожидает уже запущенный сервер на порту 3107 (либо адрес в `TEST_BASE_URL`) и создаёт двух тестовых пользователей:

```bash
TEST_BASE_URL=http://127.0.0.1:3107 pnpm test:api
```

WebSocket endpoint работает на том же порту, что и REST, и использует API этого
же экземпляра как единственную реализацию операций:

```bash
PORT=3107 pnpm start
TEST_BASE_URL=http://127.0.0.1:3107 TEST_WS_URL=ws://127.0.0.1:3107/ws pnpm test:ws
```

## Голосовые комнаты и presence

Веб-клиент открывает тот же `/ws`, первым кадром отправляет токен и получает
protocol 2. Устройство продолжает использовать protocol 1 с токеном в заголовке.
Голосовая сессия привязана к паре пользователей: первый участник создаёт комнату,
второй принимает приглашение один раз, после чего оба могут выходить и возвращаться,
пока в комнате остаётся собеседник. Потеря WebSocket не считается выходом — сервер
держит владение вкладки 45 секунд и позволяет восстановить сигналинг без нового
принятия. Метаданные комнат и `lastSeenAt` лежат в `data/realtime.json`; SDP, ICE,
медиапотоки и resume-токены на диск не записываются.
Служебный `MESSENGER_INTERNAL_TOKEN` для вызова push-маршрута генерируется при
запуске общего процесса и в поддерживаемой однопроцессной схеме настройки не требует.

Перед созданием комнаты интерфейс запрашивает микрофон и показывает выбор входа и
выхода. В браузерах без `setSinkId` (в том числе старых iOS) аудиовыход выбирается
системой. Для связи за NAT настройте coturn и `RTC_TURN_URLS` + `RTC_TURN_SECRET`;
сервер выдаёт часовые HMAC credentials через авторизованный `GET /api/rtc/config`.
Один STUN не гарантирует установку связи в мобильных и корпоративных сетях.

В production compose уже включён coturn на `3478/tcp+udp` с relay-диапазоном
`49160-49200/tcp+udp`. Перед запуском заведите DNS-запись для TURN, например
`turn.example.com`, откройте эти порты у провайдера и задайте в `.env` один общий
секрет и URL:

```dotenv
RTC_TURN_SECRET=<случайный секрет длиной не менее 32 байт>
RTC_TURN_URLS=turn:turn.example.com:3478?transport=udp,turn:turn.example.com:3478?transport=tcp
```

Тот же домен укажите в `realm` внутри `deploy/turnserver.conf`: он участвует в
HMAC-подписи временных credentials, поэтому значения по обе стороны должны совпадать.

Конфигурация рассчитана на сервер с публичным IP непосредственно на сетевом
интерфейсе: coturn сам выбирает relay-адрес. Если TURN окажется за NAT, явно
задайте соответствие публичного и приватного адресов через `external-ip`.

Не добавляйте `RTC_TURN_SECRET` в git: это одновременно ключ coturn и ключ,
которым приложение подписывает временные TURN credentials.

На iOS PWA звонок поддерживается в foreground. После приостановки или выгрузки
приложения push только открывает комнату, а микрофон включается повторным действием
пользователя — веб-приложение не обещает поведение нативного CallKit в фоне.

## Авторизация REST API

Во всех закрытых ручках передавайте один из заголовков:

```http
Authorization: Bearer msg_ваш_токен
```

или более удобный для микроконтроллера:

```http
X-API-Key: msg_ваш_токен
```

Все ответы имеют одну форму:

```json
{ "ok": true, "data": {} }
```

или:

```json
{ "ok": false, "error": { "code": "invalid_token", "message": "..." } }
```

### Профиль

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/auth/register` | Создать профиль, тело `{ "name": "Аня" }`; токен возвращается только здесь |
| `POST /api/auth/session` | Восстановить профиль, тело `{ "token": "msg_..." }` |
| `GET /api/me` | Текущий пользователь |
| `PATCH /api/me` | Поменять имя и аватарку, тело `{ "name": "Аня", "avatarUrl": "https://example.com/avatar.jpg", "avatarBackground": "#DCEBFA" }`; пустые `avatarUrl` и `avatarBackground` удаляют изображение и выбранный фон |
| `POST /api/me/token` | Сбросить токен и получить новый сгенерированный сервером; старый сразу перестаёт работать |
| `GET /api/users/:uuid` | Найти публичное имя и аватарку пользователя |

### PWA и уведомления

Приложение содержит web app manifest, адаптивные иконки и service worker. Его
можно установить из браузера; сохранённая оболочка открывается и без сети, но
для загрузки диалогов по-прежнему требуется соединение с сервером.

Для фоновых уведомлений создайте VAPID-ключи:

```bash
pnpm push:keys
```

Перенесите выведенные ключи в `.env` или окружение VPS как
`WEB_PUSH_VAPID_PUBLIC_KEY` и `WEB_PUSH_VAPID_PRIVATE_KEY`. В
`WEB_PUSH_VAPID_SUBJECT` укажите контактный `mailto:` или HTTPS-адрес. Без этих
переменных PWA продолжит работать, а в настройках будет указано, что push на
сервере пока не настроен.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/push` | Проверить серверную настройку push и получить публичный VAPID-ключ |
| `POST /api/push` | Сохранить браузерную подписку: `{ "subscription": PushSubscriptionJSON }` |
| `DELETE /api/push` | Удалить подписку текущего браузера: `{ "endpoint": "https://…" }` |

Подписки хранятся в `store.json`. Сервер автоматически удаляет недействительные
endpoint-ы после ответов push-сервиса `404` или `410`. При выходе из браузера
клиент также удаляет свою подписку.

Сервер хранит только SHA-256 хеш токена. После потери токена восстановить доступ без прямого редактирования JSON нельзя.

### Контакты

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/contacts` | Список контактов текущего пользователя |
| `POST /api/contacts` | Добавить: `{ "userId": "uuid" }` |
| `DELETE /api/contacts/:uuid` | Удалить только из своего списка |
| `POST /api/sync` | Один web-запрос: контакты, история, скрытые диалоги и отметка доставки |
| `DELETE /api/conversations/:uuid` | Скрыть диалог (`{ "mode": "hide" }`) или удалить историю (`{ "mode": "delete_history", "scope": "me" | "everyone" }`) |

### Сообщения

Обычное сообщение:

```http
POST /api/messages
X-API-Key: msg_sender_token
Content-Type: application/json

{
  "toUserId": "UUID получателя",
  "kind": "text",
  "text": "Я уже рядом"
}
```

Вопрос для физических кнопок:

```json
{
  "toUserId": "UUID получателя",
  "kind": "choice",
  "text": "Будешь чай?",
  "options": [
    { "id": "1", "label": "Да" },
    { "id": "2", "label": "Нет" }
  ]
}
```

ID варианта задаёт отправляющий клиент и должен быть уникальным внутри сообщения. Он не описывает кнопку или положение варианта в интерфейсе.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/messages?box=all&contactId=UUID&limit=50` | История без изменения статусов; `box`: `all`, `inbox`, `sent` |
| `GET /api/messages/:uuid` | Одно доступное отправителю или получателю сообщение |
| `DELETE /api/messages/:uuid` | Удалить одно сообщение: `{ "scope": "me" | "everyone" }` |
| `DELETE /api/messages` | Удалить несколько сообщений: `{ "ids": ["uuid"], "scope": "me" | "everyone" }` |
| `POST /api/messages/poll` | Получить непрочитанные входящие и атомарно поставить `delivered` |
| `PATCH /api/messages/:uuid/status` | Тело `{ "status": "read" }` или `{ "status": "delivered" }` |
| `POST /api/messages/:uuid/answer` | Выбрать вариант: `{ "id": "2" }` |

`answer` автоматически проставляет также `delivered` и `read`. Повтор того же ID идемпотентен, смена уже данного ответа возвращает `409`.

При `scope: "me"` сообщение остаётся доступно второму участнику, но больше не возвращается текущему пользователю ни в истории, ни в device poll. При `scope: "everyone"` запись удаляется из общего хранилища. Ответ на вопрос хранится внутри записи вопроса и удаляется вместе с ним.

Скрытие диалога не удаляет контакт или сообщения. `POST /api/sync` возвращает UUID скрытых собеседников в `hiddenPeerIds`; новое сообщение между участниками снова открывает диалог. Удаление всей истории дополнительно скрывает пустой диалог: только у текущего пользователя при `scope: "me"` и у обоих при `scope: "everyone"`.

## WebSocket device adapter

WebSocket — единый транспорт устройства для сообщений, погоды и валют. Подключение к
`/ws` на общем порту приложения авторизуется заголовком `X-API-Key` (также поддерживается
`Authorization: Bearer ...`). Токен не передаётся в URL. REST остаётся
доступным и является единственной реализацией чтения и изменения состояния;
адаптер не хранит собственную копию сообщений. Погода wttr.in и курсы fxapi
запрашиваются уже с VPS, поэтому ESP8266 не создаёт отдельные TLS-соединения к
внешним сервисам. Для wttr.in используется равноценный резервный домен wttr.is,
а Open‑Meteo остаётся аварийным источником погоды и дополняет четвёртый день
прогноза, которого нет в ответе wttr.in.

Сервер отправляет:

- `{"type":"ready","protocol":1,"userId":"..."}` после проверки токена;
- `{"type":"inbox_snapshot","ok":true,"data":{"messages": [...]}}` при
  подключении и при изменении непрочитанных сообщений;
- `{"type":"ack","requestId":"...","action":"read","ok":true}` после
  команды устройства;
- `{"type":"dashboard_snapshot","requestId":"...","ok":true,"weather":{...},"rates":{...}}`
  с нормализованной погодой и курсами;
- `{"type":"error","error":{"code":"...","message":"..."}}` при ошибке
  фоновой синхронизации.

Устройство может отправить:

```json
{ "type": "refresh" }
{ "type": "read", "requestId": "1", "messageId": "message-uuid" }
{ "type": "answer", "requestId": "2", "messageId": "message-uuid", "id": "option-id" }
{ "type": "send", "requestId": "3", "toUserId": "user-uuid", "text": "Хорошо" }
{ "type": "dashboard_refresh", "requestId": "4", "weather": true, "rates": true, "latitude": 44.8176, "longitude": 20.4633 }
```

Для готового короткого ответа поле `readMessageId` в событии `send` позволяет
после отправки отметить исходное входящее прочитанным. В `answer.id` по-прежнему
передаётся настоящий ID серверной опции, а не кнопка, индекс или подпись.
Максимальный входящий WS-кадр адаптера — 16 КБ; heartbeat разрывает зависшие
соединения. Внутренний poll по умолчанию выполняется раз в 2 секунды и отправляет
полный inbox-снимок только когда набор ожидающих сообщений изменился.
Погода кешируется адаптером на 10 минут по округлённым координатам, курсы — на
один час. Несколько устройств или повторные refresh поэтому не умножают число
внешних запросов. Координаты проверяются адаптером; токен по-прежнему не попадает
ни в URL внешних сервисов, ни в логи.

## Рекомендуемый цикл ESP

1. Раз в 2–5 секунд вызвать `POST /api/messages/poll` с телом `{}` и `X-API-Key`.
2. Отобразить полученный список или выбранный элемент. Устройство не обязано сохранять сообщения и статусы во flash: источником состояния остаётся сервер, а доступ восстанавливается по токену. Poll возвращает актуальные непрочитанные входящие; историю можно заново получить через `GET /api/messages?box=inbox`.
3. После явного действия средней кнопкой отправить `PATCH .../status` со статусом `read`.
4. Для `kind: "choice"` клиент сам сопоставляет элементы массива своим кнопкам или меню и отправляет строковый ID выбранной опции через `POST .../answer`. Сейчас сервер принимает ровно две опции; веб-клиент назначает им компактные ID `"1"` и `"2"` в порядке массива.
5. Если массив пуст, оставить экран ожидания.

Пример poll:

```bash
curl -sS -X POST https://example.com/api/messages/poll \
  -H 'X-API-Key: msg_your_token' \
  -H 'Content-Type: application/json' \
  -d '{"limit":10}'
```

## VPS через Docker

```bash
docker compose up -d --build
```

JSON лежит в конкретной папке `./data/store.json` рядом с `docker-compose.yml`. При первом старте entrypoint поправит права каталога, а само приложение продолжит работать не от root. Перед обновлением сервера достаточно скопировать папку `data`. За HTTPS и реальные IP клиентов должен отвечать reverse proxy (Caddy или nginx), который передаёт `X-Forwarded-For`.

Compose публикует приложение только на `127.0.0.1:3000`, чтобы порт нельзя было обойти снаружи. Контейнерный reverse proxy может подключаться к сети `<compose-project>_default` и обращаться к сервису как `messenger:3000`.

WebSocket endpoint опубликован вместе с приложением на `127.0.0.1:3000`. Для
nginx добавьте к существующему HTTPS virtual host:

```nginx
location /ws {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
}
```

TLS завершается на reverse proxy, поэтому устройство подключается к
`wss://example.com/ws`, а приложение внутри VPS принимает обычный WebSocket. После
обновления выполните `docker compose up -d --build` и проверьте Upgrade через
`pnpm test:ws`, указав `TEST_WS_URL=wss://example.com/ws`.

Настраиваемые переменные находятся в `.env.example`. Общие ограничения частоты хранятся в памяти и рассчитаны на один процесс: по умолчанию 120 публичных и 480 авторизованных запросов в минуту на комбинацию IP/токена. Для отправки сообщений действует отдельный лимит на пользователя: 6 сообщений за 10 секунд и 30 сообщений в минуту. При превышении `POST /api/messages` возвращает `429`, код `message_rate_limited` и заголовок `Retry-After`. Это защищает от случайного зажатого Enter, но не является DDoS-защитой.

## Границы текущего MVP

- JSON-хранилище и внутренняя очередь записи требуют одного экземпляра Node.js. Для горизонтального масштабирования нужна настоящая БД.
- Веб раз в 5 секунд делает `POST /api/sync` для сообщений и профилей. Presence и голосовой сигналинг идут через общий WebSocket; сообщения пока сохраняют совместимый REST polling.
- Нет восстановления утерянного токена, блокировок пользователей, антиспама и сквозного шифрования.
- Нет горизонтального масштабирования realtime без внешней БД/pub-sub; background-звонки на iOS работают только как push-to-open.
